## 生活场景切入

问大模型：「我们公司年会改到 12 月 21 日了，那天星期几？」

普通聊天机器人：可能编一个答案（它不知道你们公司的日期，G2 幻觉机制）。

Agent 的做法完全不同：

```text
🤔 思考：我需要先查公司年会的日期，再算星期几
🔧 行动：调用搜索工具 → 查到「2026年12月20日晚上6点」
👁 观察：日期拿到了，但用户问的是改期后的 21 日
🤔 思考：需要日历计算——调用计算/日历工具
🔧 行动：调用工具 → 得到 12 月 21 日是星期一
💬 回答：「改期后的 12 月 21 日是星期一。」
```

区别一目了然：**聊天机器人只有嘴，Agent 有手**。它能拆解任务、调用外部工具、根据反馈调整计划，循环直到目标达成。

## 核心概念拆解

### 概念 1：ReAct —— Agent 的心跳循环

主流 Agent 框架的骨架叫 **ReAct**（Reasoning + Acting），三个节拍循环往复：

```text
Thought（思考）：我现在知道什么？下一步该干什么？
Action（行动）： 调用某个工具
Observation（观察）：工具返回的结果

→ 把 Observation 并入上下文，回到 Thought，直到能给出最终答案
```

实测的玩具轨迹（实际运行输出）：

```text
🤔 thought: 用户问年会改到 12 月 21 日后是星期几。我需要先查年会日期…
🔧 action:   search("公司年会时间")
👁 observe:  2026年12月20日晚上6点
🤔 thought:  用户说的是改期后的 12 月 21 日。需要算星期几。
🔧 action:   calculator("(20+1)")
👁 observe:  21
```

机制本质：**把 CoT 思维链（NLP8）升级成能与外部世界交互的版本**——推理不再只发生在文本内部，每一步都可以伸手拿新信息。模型负责「决定调什么工具、传什么参数」，执行与环境反馈交给框架。

### 概念 2：工具调用（Function Calling）的机制

现代大模型 API 原生支持工具调用。开发者注册一组工具（名称+功能描述+参数格式），模型的输出就可以是结构化的「调用指令」：

```json
{
  "tool": "search",
  "arguments": { "query": "公司年会时间" }
}
```

注意一个容易误解的点：**模型并不真的执行任何东西**——它只是生成一段「我想调用 XX 工具」的结构化文本；真正执行的是你的代码，执行结果再喂回给模型。安全边界由此清晰：

| 设计原则         | 理由                                |
| ---------------- | ----------------------------------- |
| 最小权限         | 只暴露任务必需的工具                |
| 危险操作要确认   | 删文件、付款类动作必须人工点头      |
| 工具描述要精准   | 模型靠描述选工具，含糊描述=错误调用 |
| 设置最大循环次数 | 防止 Agent 陷入死循环烧钱           |

### 概念 3：规划与分解 —— Agent 的智力上限在哪

复杂任务的成败在行动之前就决定了：**任务拆解的质量**。

```text
「帮我调研竞品并写份报告」
  ↓ Agent 的隐性规划
① 列出竞品名单（模型内部知识/搜索）
② 逐个搜集信息（多次搜索工具）
③ 提炼对比维度（推理）
④ 撰写报告（生成长文）
```

两个现实约束要认清：

1. **规划质量受模型能力制约**：拆解漏了一个关键步骤，后面全白干——这也是为什么前沿 Agent 都配最强的底座模型
2. **误差会滚雪球**：十步任务里每步 95% 正确率，全程正确率只剩约 60%（0.95¹⁰≈0.60）——长链条任务是 Agent 的软肋，人工检查点不可或缺

### 概念 4：多 Agent 协作 —— 分工还是内耗？

进阶玩法：让多个 Agent 各司其职（调研员/写手/审稿人）互相协作。听起来美好，实践中的经验法则更冷静：

```text
✅ 多 Agent 有用的场景：角色视角确实不同（如「红队找茬 vs 蓝队辩护」）、
   任务可真并行（同时调研五个竞品）
⚠️ 常见的失败模式：简单任务强行分工 → 沟通开销 > 分工收益；
   「审稿 Agent」客气地放水 → 形式主义流水线
```

本站的多 Agent 宪章（数学/英语/AI/青年大学习/审查五线并行）就是一个真实案例——它的成立前提是各线目录隔离、共享文件有冲突规则、Reviewer 在独立会话审查。**没有这些配套纪律，多 Agent 只是昂贵的混乱。**

### 概念 5：什么时候该用 Agent —— 决策清单

Agent 是重型武器，上之前过一遍清单：

```text
✅ 适合：多步骤、需要外部信息/工具、路径无法预先穷举的任务
   （深度调研、数据清洗流水线、客服工单分诊）
❌ 不适合：
   单轮问答 → 直接问就行，套 Agent 是脱裤子放屁
   步骤固定的工作流 → 写死代码更可靠更便宜
   高风险不可逆操作 → 全自动 = 全速闯祸
```

一句话定位：**Agent 用推理灵活性换取可靠性——只在灵活性值钱的时候付这个价。**

## 自测一下

> [!question]- 1. 「模型并不真的执行工具」——那么一次完整的工具调用中，控制权如何流动？
> 流程四拍：① 模型输出结构化调用请求后**暂停**；② 控制权回到你的框架代码，由它解析请求并实际执行函数；③ 执行结果作为新的 Observation 文本追加进对话历史；④ 控制权交回模型继续推理。
> 这个设计的妙处：模型永远不直接触碰系统——所有危险操作的闸门都在你的代码手里。理解这一点才能正确设计权限与审计。

> [!question]- 2. 十步任务每步 95% 可靠，整体成功率约 60%。给出两条工程对策并说明各自的作用原理。
> 对策① **插入人工检查点**：把十步切成两三段，段间人工确认——每段的错误被拦截不向后传播，把「连乘」变成「分段验证」。
> 对策② **每步加自检/重试**：让 Agent 每步产出后自查或用校验工具验证，失败自动重试——等效提升单步可靠率 p；由于 0.99¹⁰≈0.90，把单步提到 99% 就能把整体从 60% 拉回 90%。
> 共同思想：**串联系统的可靠性管理 = 打断连乘结构**（并联冗余或分段门控），这与硬件容错设计同源。

> [!question]- 3. 为什么说「工具描述写得含糊」是 Agent 出错的重灾区？结合模型的选择机制说明。
> 模型选择工具的依据只有一个：你在注册时写的功能描述文本。它是模型眼里的「使用说明书」。
> 含糊后果实例：两个工具都写着「查询信息」——模型面对「查订单状态」时只能瞎猜，选错则后续全部作废。好的描述三要素：**适用场景（何时用）、参数语义（传什么）、边界（不要用于什么）**。这本质是 NLP8 提示词工程的延伸：**工具描述就是给模型看的提示词**。

> [!question]- 4. 老板要求「做一个全自动 Agent 盯盘炒股，亏钱了自动止损卖出」。评估这个需求。
> 强烈不建议全自动。逐条分析：
> ① **不可逆高风险操作**：真实资金交易，幻觉/误判的直接后果是真金白银——违反最小风险原则；
> ② **误差累积放大**：盯盘是长时间链条任务，0.95^N 的衰减定律下运行越久越危险；
> ③ **极端场景超出训练分布**：黑天鹅行情下模型的统计直觉最不可靠，恰恰是最需要行动的时刻。
> 改良方案：Agent 只做**分析与建议**（信号提示、风险评估报告），下单决策与执行保留人工；或先以纸面模拟盘运行积累置信度。「人机协同」不是保守，是对误差累积数学的基本尊重。
