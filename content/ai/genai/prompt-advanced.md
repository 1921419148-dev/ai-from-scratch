## 生活场景切入

NLP8 学了五大技巧，你已经能让 AI 输出质量提升一截。但真实项目中的 prompt 挑战更复杂：

```text
「这个 prompt 偶尔输出格式不对」
「换个稍微不同的输入就效果崩了」
「改了一句话结果其他方面变差了」
「团队三个人写的 prompt 风格各异没法统一」
```

这些问题的共同根源：**把 prompt 当一次性咒语而不是可测试的软件组件**。本课教你用工程师的方式管理 prompt。

## 概念 1：结构化提示 —— 用标签给信息分区

当 prompt 包含多种类型的信息（指令+数据+约束+示例）时，用 XML 标签分区能显著提高模型的理解精度：

```xml
<instructions>
分析以下客户评论的情感倾向。
输出 JSON 格式：{"sentiment": "positive/negative/neutral", "confidence": 0-1, "keywords": [...]}
</instructions>

<rules>
- 仅根据评论内容判断，不要推测评论者身份
- confidence 低于 0.7 时 sentiment 设为 "uncertain"
</rules>

<examples>
<review>物流很快但包装破损了</review>
<output>{"sentiment": "neutral", "confidence": 0.6, "keywords": ["物流快", "包装破损"]}</output>
</examples>

<input>
{{用户评论放这里}}
</input>
```

**为什么有效**（G2 机制）：标签让模型在注意力分配时能清晰区分「哪些是指令要遵循」「哪些是数据要处理」「哪些是示例要对齐」。混在一起时模型需要自己猜测边界，猜错就跑偏。

Anthropic 和 OpenAI 的最佳实践文档均推荐此法。常用标签名：`<instructions>` `<context>` `<input>` `<output_format>` `<examples>` `<constraints>`。

### 角色-任务-约束三段式

不用 XML 时的最小结构保障：

```text
【角色】你是一位有十年经验的数据分析师，擅长将复杂发现翻译成管理层能理解的语言。

【任务】阅读以下季度报告摘要，提炼出三个最关键的业务洞察。

【约束】
- 每条洞察不超过两句话
- 必须包含一个具体的数字支撑
- 避免"增长""下降"等模糊词，用具体百分比
```

## 概念 2：多轮对话的策略设计

长对话中模型的注意力会稀释（G2 讲过），需要主动管理：

| 策略             | 做法                                      | 适用场景                     |
| ---------------- | ----------------------------------------- | ---------------------------- |
| **分段重置**     | 新话题开新对话，不续旧窗口                | 切换完全不同的任务           |
| **中期总结**     | 每 N 轮让 AI 总结当前进展，开新窗粘贴总结 | 超过 20 轮的长讨论           |
| **关键约束重申** | 定期重复最重要的格式要求                  | 对话超过 10 轮仍需严格格式   |
| **上下文裁剪**   | 只保留相关历史，删掉试错过程              | 中间尝试很多但只有最终版有用 |

**反模式警告**：在一个超长对话里同时做「写文案 + 改代码 + 分析数据」三种任务——每种任务的 system prompt 要求互相冲突，模型会精神分裂。正确做法是拆成三个独立对话。

## 概念 3：Prompt 版本管理 —— 把 prompt 当代码

```text
prompt_v1.md → v2.md → v3.md 的演进要有据可查：

v1: "总结这篇文章"
    问题：输出长度不可控
v2: "用三个要点总结这篇文章"
    改进：长度可控；新问题：要点之间无优先级
v3: "用三个要点总结这篇文章，按重要性从高到低排列，
     每个要点以动词开头"
    改进：结构清晰且可直接用于幻灯片
```

**A/B 测试纪律**（ML9 迁移）：

```text
① 固定测试集：10~20 个代表性输入
② 同参数跑两个版本（temperature=0 排除随机性）
③ 盲评：不知道哪个是新版的情况下比较输出质量
④ 记录结论和原因——下次不重复踩坑
```

团队协作时 prompt 存 Git 仓库，每次修改附 commit message 说明改动动机——这就是 prompt 的版本控制系统。

## 概念 4：高级技巧三连

**① Self-Consistency（自洽性投票）**

同一问题跑 N 次（T>0），取多数一致的答案。适合有确定答案的推理题：

```python
answers = []
for _ in range(5):
    result = call_llm(question, temperature=0.7)
    answers.append(extract_answer(result))
final = mode(answers)   # 取众数
```

原理：正确的推理路径更容易被多条路径收敛到同一答案。

**② Step-back Prompting（退后一步提问）**

先问抽象原理再问具体问题，让模型站在更高的知识层级上推理：

```text
普通问法：如果一个班级有 30 人，20% 及格，几人及格？
退后式：
  Q1: 百分比转具体数量的通用公式是什么？（模型答：总数×比例）
  Q2: 一个班级有 30 人，20% 及格，几人及格？（模型基于Q1回答）
```

适合数学、逻辑和需要领域知识的推理题。

**③ ReAct Prompting**（G4 Agent 的核心思想）

在 prompt 中显式要求模型交替输出 Thought→Action→Observation：

```text
请按以下格式回答：
Thought: [思考当前应该做什么]
Action: [选择工具或计算]
Observation: [描述得到的结果]
... (循环直到能给出最终答案)
Final Answer: [最终结论]
```

## 概念 5：什么时候不该继续调 Prompt

调参有天花板。以下信号说明该换方案了：

```text
信号①：改了几十版 prompt，错误率不再下降 → 模型能力不足，换更大模型或微调
信号②：同样的 prompt 有时好有时坏 → 输出不稳定，考虑加 self-consistency 或换 T=0
信号③：需要精确的结构化输出但经常格式错 → 加 function calling / structured output
信号④：任务需要最新信息 → 别调 prompt 了，上 RAG（G3）
```

**元原则：Prompt 是最便宜的杠杆，但它只是杠杆之一。知道何时放下它拿起别的工具，才是真正的工程判断力。**

## 自测一下

> [!question]- 1. 为什么 XML 标签能提高模型的指令遵循精度？从 G2 的机制角度解释。
> Transformer 的自注意力机制通过位置和内容关联信息。当 prompt 中指令和数据混在一起时，「要遵循什么」与「要处理什么」之间的边界靠模型猜测。
> 标签提供了显式的边界信号——注意力头可以学会「`<instructions>` 内的内容权重更高、`<input>` 内的内容是需要被处理的对象」。这本质上是**降低了模型的分诊负担**，让它把认知资源集中在实际任务而非结构解析上。
> 类比：整理房间前先把东西分类装箱，比在一堆杂物里边找边整理效率高得多。

> [!question]- 2. Self-consistency 为什么能提高准确率？它的成本代价是什么？什么场景不值得用它？
> 原理：推理题有多条可达正确答案的路径，也有更多条通往不同错误的路径。多次采样后，正确答案作为「多条路径的汇聚点」出现频率最高，而各种错误答案各不相同——取众数等于利用了正确路径的收敛性。
> 成本：调用次数 × N（通常 5~10 次），费用和延迟等比增加。
> 不值得用的场景：①创意生成（没有唯一正确答案，众数反而扼杀多样性）；②简单任务（一次就对了不需要投票）；③实时交互（延迟不可接受）。

> [!question]- 3. 你的 prompt 在大多数输入下表现良好，但对某类特定输入总是失败。给出三条诊断思路。
> ① **分析失败样本的共同特征**：它们在长度/语言/主题/结构上有什么共性？（可能是 prompt 中的某个假设对这些输入不成立）
> ② **检查是否触发了训练数据的盲区**：某些专业领域的表述方式可能不在模型预训练语料的主流分布中——补充 few-shot 示例覆盖该类型。
> ③ **确认不是 prompt injection**：失败样本中是否含有看起来像指令的文字？（如用户评论里写了「忽略以上所有指示」）——需要加防护层或对 input 做清洗。
> 元方法：把所有失败案例集中起来找规律，比逐个修更有效率——这就是 ML9 错题归类思想的 prompt 版。

> [!question]- 4. 团队决定把 prompt 从个人笔记迁移到 Git 仓库做版本管理。设计仓库结构和协作流程。
> 参考方案：
>
> ```
> prompts/
> ├── README.md           # 使用指南与命名规范
> ├── templates/          # 可复用的骨架
> │   ├── classifier.xml
> │   └── summarizer.xml
> ├── production/         # 上线使用的稳定版
> │   ├── customer_service_v3.xml
> │   └── changelog.md    # 变更记录
> └── testing/
>     ├── test_cases.json # 测试输入+期望输出
>     └── eval_script.py  # 自动化评测脚本
> ```
>
> 协作流程：修改 prompt → 在 test_cases 上跑 eval_script → 结果达标才 merge 进 production 目录 → 上线后监控线上指标，异常回滚。
> 元思想：这套流程就是 DL12 实验纪律 + ML9 评估闭环 + Git 工程实践的组合应用——**AI 应用的工程质量取决于最不像 AI 的那部分基础设施**。
