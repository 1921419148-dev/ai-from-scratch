## 生活场景切入

你在对话框输入「帮我写一首关于春天的诗」，回车。三秒后，一首像模像样的诗逐字浮现。

这三秒里发生的事，是本板块所有应用的物理基础。好消息是：拆开看没有一步是你没学过的——NLP1 分词、DL9 Transformer、NLP7 自回归采样，今天只做一件事：**把它们串成一条完整的流水线**。

## 核心概念拆解

### 概念 1：六步流水线 —— 从回车到第一个字

```text
① 切分 Tokenization：「帮我写一首关于春天的诗」→ [帮][我][写]…[诗]
② 编码 Embedding：每个 token → 向量 + 位置信息        （DL9 位置编码）
③ 预填充 Prefill：整段提示并行过一遍网络              ← 快，一次性
④ 解码 Decode：循环「算分布 → 采样一个词 → 拼回输入」  ← 逐字慢，每字一遍网络
⑤ 采样控制：temperature/top-p 调节随机性             （NLP7）
⑥ 流式返回：每个新 token 立刻推送到你的屏幕          ← 所以字是一个个蹦的
```

关键性能洞察藏在 ③④ 的不对称里：

```text
Prefill（读你的提示）：并行处理全部 token —— GPU 满血，飞快
Decode（写回答）    ：每生成一个 token 都要跑一遍完整网络 —— 串行瓶颈
```

所以大模型 API 的账单永远是两栏：**输入便宜、输出贵**（通常差数倍）。这也是为什么优化提示词（删冗余）比优化回答（让它短点）在成本上更划算——虽然两者都该做。

### 概念 2：上下文窗口 —— 昂贵的金鱼记忆

模型能「看见」的范围只有当前对话的 token 总量（现代模型从 8K 到百万级 token 不等）。三个必须内化的推论：

1. **超出窗口的早期对话彻底遗忘**——聊得越久越「失忆」，不是玄学是机制
2. **窗口内也有注意力稀释**：大海捞针实验显示长上下文中部的信息利用率显著偏低（DL8 的 O(n²) 与 softmax 配额竞争）
3. **每一轮对话都携带全部历史重新计费**——第 20 轮时你在为前 19 轮的全部内容付输入费

工程对策预告：历史压缩总结、外部记忆库（RAG）、多 Agent 分工——GenAI 后续课程的核心议题都源于这条内存约束。

### 概念 3：幻觉 —— 从机制上理解「一本正经地胡说八道」

幻觉（模型编造不存在的事实、引用、数据）常被误解为 bug。从生成机制看，它是**设计目标的自然产物**：

```text
模型的训练目标：给定前文，产出统计上最合理的下一个 token
它学到的是     ：语言模式的流畅性
它没学到的     ：真值校验器——没有任何内部模块专门负责「这话是真的吗」
```

于是当被问到训练数据稀疏的细节（某小众论文的第几页写了什么），模型的采样过程依然会流畅地产出「看起来最合理」的内容——**编得越像，恰恰说明语言能力越强**。三类高发场景：

| 场景           | 为什么危险             | 例                   |
| -------------- | ---------------------- | -------------------- |
| 冷门事实       | 训练信号弱             | 编造不存在的文献引用 |
| 数字与日期     | 语言模型对精确值不敏感 | 「约 37%」实为编造   |
| 长链条推理后期 | 早期小错滚雪球         | 推理三步后的结论失真 |

对策分层（后续课程展开）：RAG 提供可靠资料源（G3）、要求引用来源并核对、关键场景人工复核（G8）。

### 概念 4：Token 经济学的实用账本

把机制翻译成省钱技巧：

```text
✅ 系统提示词精炼复用（每次调用都在重复计费）
✅ 长文档先检索再注入，而非全文粘贴（G3 RAG 的动机之一）
✅ 让输出「用要点列表、不超过 200 字」（输出 token 是大头）
⚠️ 多轮长对话适时开新会话（甩掉历史包袱）
```

以及一个反直觉提醒：**换更便宜的模型常常是最优解**——大量日常任务（改错别字、格式转换）根本不需要旗舰模型，分级路由能省 90% 成本。

## 自测一下

> [!question]- 1. 为什么大模型 API 的输出价格通常是输入的好几倍？用 prefill/decode 机制解释。
> 输入侧走 prefill：全部 token 一次并行计算，GPU 利用率高。
> 输出侧走 decode：每生成一个 token 就要完整跑一遍网络且严格串行（下一个词依赖上一个词），GPU 大量时间花在等待与访存而非计算上。
> 同样多的 token，decode 的实际计算时间与资源占用远超 prefill——定价反映成本结构。（KV cache 缓解但未消除这一不对称。）

> [!question]- 2. 「聊得越久模型越笨」的用户体验，列出两个机制层面的原因。
> ① **硬遗忘**：总 token 超出上下文窗口后，最早的对话被截断出窗——模型真的看不见了；
> ② **软稀释**：即使还在窗口内，超长历史的注意力竞争使关键早期约束（如最初设定的格式要求）权重被稀释，模型行为漂移。
> 对策：重要约束在长对话中定期重申；或主动总结压缩历史后开新会话。

> [!question]- 3. 为什么问大模型「今天是几号」「现在几点」经常答错甚至答出固定日期？这揭示了什么结构性限制？
> 因为模型只看得见上下文窗口内的文本——而系统提示里未必注入了当前时间；它的「知识」冻结在训练数据截止日。
> 这揭示的是：**语言模型天生是封闭系统的文本处理器，不连接任何实时世界**。联网搜索、时钟注入等都是外挂机制（Agent 工具调用的雏形，G4 展开）。「模型不知道现在几点」与「模型不知道你的公司制度」是同一堵墙。

> [!question]- 4. 同事提议「把公司 wiki 全文贴进系统提示，让 AI 客服随时查阅」。给出至少三个反对理由和替代方案。
> 反对：① 窗口放不下或挤占业务对话空间；② 每次调用重复计费全部内容，成本失控；③ 注意力稀释导致检索质量反而不如专业方案；④ wiki 更新需改动所有调用配置。
> 替代：**RAG 架构**——wiki 切片建向量索引，按问题动态检索 top-k 片段注入。这正是下一课的主题，本题为它提供了全部动机。
