## 生活场景切入

API 很方便，但总有场景让你想拥有自己的模型：

```text
① 数据不能出门：医院病历、律所卷宗、未发布产品资料——隐私红线
② 成本算不过来：每天百万次调用，API 账单比养模型还贵
③ 需要定制行为：固定的输出格式、领域黑话、企业人格
```

好消息是 2023 年后，「个人/小团队拥有自己的大模型」从科幻变成了周末项目。这一课就是操作手册。

## 核心概念拆解

### 概念 1：先问要不要微调 —— 三个判断信号

DL10 讲过原理，这里讲决策。依次检查：

```text
信号① 提示词已经调到极限了吗？
   很多「需要微调」的需求，其实一个精心设计的 few-shot 就解决了。
   先穷尽 prompt（NLP8），再谈微调。

信号② 需要改变的是知识还是行为？
   知识（新事实）→ RAG（G3），微调灌知识不可靠
   行为（风格/格式/任务模式）→ ✅ 这才是微调的主场

信号③ 有多少高质量标注数据？
   <500 条 → 大概率不够，先攒数据或继续用 prompt
   1000~10000 条 → LoRA 微调的甜蜜区间
```

三关都过才动工——**微调是重武器，误用的代价是过拟合 + 维护负担 + 一堆只有你能修的坑**。

### 概念 2：LoRA 微调实战流程

以「给开源模型注入你们公司的客服话术风格」为例：

```text
① 准备数据：500~5000 条 (客户问题, 理想回答) 对，
   格式统一为对话模板；质量 > 数量（脏数据微调 = 强化错误）

② 选底座：开源模型按显存选型（7B 级最通用）

③ LoRA 配置：
   目标模块：注意力层的投影矩阵（默认全加）
   秩 rank：8~64（越大越能学复杂模式，越易过拟合）
   学习率：1e-4 ~ 2e-4（比全量微调大一个量级，因为只训小矩阵）

④ 训练监控盯三样：训练 loss 平稳下降、验证 loss 不回升（ML4 早停）、
   定性抽查生成样例（数字好看但话术不对 = 白训）
```

DL10 的原理在此全部兑现：原模型权重全程冻结，只训旁路低秩矩阵——消费级显卡几小时搞定，产物是一个几十~几百 MB 的「技能补丁」而非整个模型。

### 概念 3：量化 —— 榨干每一 GB 显存

原始模型每个参数存 FP16（16 位浮点）。**量化（Quantization）** 把参数压成更低的精度：

| 精度 | 每参数字节 | 7B 模型体积 | 质量损失             |
| ---- | ---------- | ----------- | -------------------- |
| FP16 | 2          | ~14 GB      | 无（基准）           |
| Q8   | 1          | ~7 GB       | 几乎无感             |
| Q4 ★ | 0.5        | ~4 GB       | 轻微，多数场景可接受 |
| Q2   | 0.25       | ~2 GB       | 明显劣化，慎用       |

直觉：把 3.14159 存成 3.14——损失一点精度换四倍空间。Q4 是社区甜点位：**4GB 显存的笔记本跑 7B 模型、16GB 跑 70B** 全靠它。配合 GGUF 等格式，量化后的模型文件即下即用。

### 概念 4：Ollama 本地部署 —— 十分钟上手

本地跑开源模型的最低门槛方案：

```bash
# ① 安装 Ollama（官网下载，Windows/Mac/Linux 全平台）
# ② 一条命令拉模型并进入对话
ollama run qwen2.5:7b        # 拉取并运行通义千问 7B（Q4 量化约 4.7GB）

# ③ 常用管理命令
ollama list                  # 查看已装模型
ollama pull llama3.1:8b      # 再下一个 Meta 的 Llama
ollama rm old-model          # 清理

# ④ 提供 OpenAI 兼容 API（端口 11434）
curl http://localhost:11434/v1/chat/completions -d '...'
```

选型速查（2026 年视角）：

| 需求          | 推荐起点               | 显存要求 |
| ------------- | ---------------------- | -------- |
| 日常问答/写作 | 7B~9B 级（Qwen/Llama） | 8GB+     |
| 代码辅助      | 代码特调 7B~14B        | 12GB+    |
| 追求质量      | 32B~70B（量化版）      | 24GB+    |
| 古董电脑      | 1B~3B 小钢炮           | 4GB      |

注意合规一步：商用前确认所选模型的**许可证条款**（Llama/Qwen 各有细则），别让法律问题毁掉技术成果。

### 概念 5：本地 vs API —— 决策总表

| 维度       | 本地部署               | 云端 API             |
| ---------- | ---------------------- | -------------------- |
| 数据隐私   | ✅ 数据不出门          | ⚠️ 视服务商条款      |
| 边际成本   | ✅ 电费而已            | ❌ 按 token 持续付费 |
| 能力上限   | ⚠️ 开源 < 顶级闭源     | ✅ 最强模型随取      |
| 运维负担   | ❌ 自己管更新/稳定性   | ✅ 零运维            |
| 定制自由度 | ✅ LoRA/改系统提示随意 | ⚠️ 受平台限制        |

典型架构：**敏感/高频简单任务走本地小模型，复杂任务走云端旗舰，路由分流**——与 G2 的成本思想一脉相承。

## 自测一下

> [!question]- 1. 用户抱怨你微调后的客服模型「变得只会说场面话」。诊断可能原因。
> 最可能：**微调数据全是礼貌得体的正面样本**——模型学到的不是「如何服务」而是「永远客气」，遇到需要明确拒绝/澄清的场景也输出套话。
> 其他候选：① 学习率过大导致灾难性遗忘，通用能力被话术覆盖；② 数据多样性不足，模型过拟合到少数应答模式；③ 训练轮数过多（ML4 过拟合教科书）。
> 处方：数据里补充拒绝、澄清、转人工等「非场面话」样本，降学习率减轮数重训——**微调会放大你数据里的一切倾向，包括偏见与单调**。

> [!question]- 2. 为什么 Q4 量化的 7B 模型（约 4GB）能放进 8GB 显存的显卡，而 FP16 版本（14GB）不行？损失的精度去哪了？
> 显存放的是参数值本身：FP16 每个 2 字节 × 70 亿 ≈ 14GB，Q4 每个 0.5 字节 ≈ 4GB——物理体积差 4 倍，放不下就对了。
> 精度损失的本质是把连续的浮点值映射到更稀疏的格点上（类似 M1 四舍五入到两位小数）：单个参数有微小偏差，但神经网络的海量参数互相冗余，统计上大部分能力得以保留。
> 边界提醒：激活值（中间计算结果）仍需较高精度，所以 Q4 只压「存储」不完全压「计算」；且不同层对量化的敏感度不同——这就是为什么存在混合精度量化的高级玩法。

> [!question]- 3. 「本地 7B 模型 + RAG」和「直接调用云端 GPT-4 级模型」做内部知识库问答，各自的胜负手是什么？
> 本地方案的赢面：隐私（数据不出门）、边际成本趋零、延迟稳定不受网络波动；输面：7B 的理解与综合能力有限，复杂多跳问题容易答不好。
> 云端旗舰的赢面：推理质量天花板高、零运维；输面：敏感文档出域的合规风险、持续计费。
> 决策公式：**(数据敏感度 × 问题复杂度分布) 对比 (预算 × 合规要求)**。实践中常见终局是混合路由——80% 简单问题本地解决，20% 疑难升级云端，兼得两头。

> [!question]- 4. 你微调了一个 7B 模型效果很好，老板说「那把它放大到 70B 重训一遍效果岂不更好？」分析这个提议的陷阱。
> 陷阱一：**成本非线性**——显存/时间随参数增长远超线性（70B 的 LoRA 训练也需要数据中心级资源）；
> 陷阱二：**收益未必存在**——如果 7B 版本的瓶颈是数据质量而非容量（验证 loss 已贴地板），更大的模型只是更贵地学到同样的东西（DL11 幂律的前提是数据同步充足）；
> 陷阱三：**部署倒退**——70B 无法在现有用户硬件上运行，违背了当初选 7B 的部署约束。
> 正确的升级路径：先扩数据/提质量 → 验证瓶颈确实在容量（看学习曲线是否仍在下降）→ 再谈规模。「更大更好」是 Scaling Laws 的正确半句话，另半句是「前提是数据和算力跟得上」。
